# Microsoft Rewards Script — Agent Handoff

This repository supplies the standalone Microsoft Rewards Worker runtime and versioned shared contracts. The sibling `rewards-dashboard/manager` owns the Manager API, Fleet/SSH coordination and dashboard. New installations use two separate release archives; Docker/cron and the old coordinator remain compatibility paths.

## Non-negotiable invariants

- Runtime requirement is Node.js `>=24.0.0`; use the repository scripts rather than inventing a second toolchain.
- Edit source under `src/` or `scripts/`, never `dist/` by hand. `dist/` is generated by `npm run build` and is ignored.
- Preserve existing user changes. Start with `git status --short`; do not reset, checkout, clean, or overwrite unrelated work.
- Never print or commit secret values from account/config files, cookies, fingerprints, diagnostics or databases. During authorized backup/migration, process them privately with restricted permissions and report counts/checks rather than values. Do not inspect secrets for unrelated tasks. Treat `config.json.bak` as sensitive even though it is currently untracked.
- Manager is not an executor. Send account/config writes to Manager (`3012` by default); worker (`3010`) receives only assigned account snapshots and runs Smart locally. Do not reintroduce dashboard cron or browser/runtime imports into Manager.
- Desktop/Mobile/Android manual actions hold only the selected account (`scope: account`). Wait only if that account is running; other accounts, including the same proxy, continue. Ordinary assignment moves still use proxy groups. Preserve the current session and return ownership after clean closure/device stop; never expire a hold automatically.
- Membership-only snapshots may apply beside unrelated running jobs only through `Hybrid.canApplyMembershipSnapshot`. Do not relax its environment/profile/config checks or globally drain a node for an idle account's manual open.
- `contintueOnBotWarning` is misspelled in the public configuration contract. Keep the spelling unless making an explicit compatibility migration across schema, examples, loader, Docker overrides and docs.
- The logger envelope and important title/message strings are consumed by `scripts/api/logParser.js`; changing them is an API change. Update parser tests and API-facing docs when necessary.
- Mobile and desktop search quotas are separate. The current quota enrichment reads the Rewards `/earn` Next/RSC payload (`pointsCounters.pc` and `pointsCounters.mobile`); an absent or malformed counter means “unavailable”, not unlimited.
- `experimental.apiSearch`, `experimental.apiSearchOnBing`, media blocking and Edge browsing have different risk and capability profiles. Do not silently enable them or present them as equivalent to browser mode.
- Authentication, Rewards server actions, fingerprinting, proxy routing and session reuse are high-risk areas. Prefer the existing helpers and recovery paths over new direct HTTP/browser code.
- Do not change `src/functions/search-queries.json` merely to make a test or build pass. It is a large runtime data asset and may have intentional user data changes.

## Standard commands

Run from the repository root:

```bash
npm install
npm run build
npm run lint
npm run test:log-parser
npm run test:search-quota
```

`test:search-quota` imports built files, so build first when running it in a clean checkout. Use `npm run dev` only with safe test accounts and an explicitly understood configuration; use `npm run ts-start` for the source entry point without the development flag. See `OPERATIONS.md` for Docker/API/manual-login commands.

## Change discipline

Before editing, identify the execution path: configuration → account load → browser/auth/session → dashboard/bootstrap → activities/search → reporting/cleanup. Trace the existing helper and logger conventions in that path. Keep changes narrow, preserve retry and refresh behavior, and add a focused regression test for parser, quota, API or log-contract changes.

After editing:

1. Run formatting/lint/build checks appropriate to the touched area.
2. Run the relevant focused test and the log parser test when logs changed.
3. Inspect `git diff --check` and `git status --short`.
4. Confirm no secret, generated `dist/`, session, diagnostic or backup file was added.
5. Summarize behavioral changes, files changed, validation, and any remaining risk.
